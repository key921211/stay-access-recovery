# AI 활용과 확인한 내용

Codex로 진행한 구현·자동 검증과 개발자가 Swagger UI에서 직접 확인한 내용을 나눠 정리했습니다.

## AI를 어떻게 활용했는지

정해 둔 문제와 제외할 기능을 바탕으로 Codex에 초기 코드와 테스트 작성을 맡겼습니다. 코드가 나온 뒤에는 소스 리뷰, 오류 재현, 수정과 재검증도 요청했습니다.

## 구현과 코드 리뷰 과정

체크인·발급 상태 조회 API, DB에 저장하는 발급 작업, 스케줄러와 Fake 도어락을 구현했습니다. 이후 소스와 테스트를 다시 읽으면서 트랜잭션 경계, 예약·작업 행 잠금, 요청 ID 재사용과 상태 전이를 살펴봤습니다. 이 구현과 코드 리뷰는 Codex가 수행했습니다.

Java 17에서 테스트와 JAR 빌드를 실행하고 로컬 HTTP 호출, 파일 H2 재시작도 확인했습니다. Swagger UI를 추가한 뒤에는 OpenAPI 생성과 브라우저에서 두 API를 호출하는 과정까지 점검했습니다.

## 발견한 문제와 수정 과정

초기 JUnit 테스트 15개와 정상 종료 후 재시작 점검은 모두 통과했습니다. 그런데 Codex의 추가 리뷰에서 체크인 `202` 응답 직후 Java 프로세스를 `SIGKILL`하자, 같은 DB를 다시 열었을 때 발급 작업은 **0건**, 예약의 `checked_in_at`은 **null**이었습니다.

H2의 기본 `WRITE_DELAY=500ms`로 디스크 쓰기가 지연된 것이 원인이었습니다. 체크인과 작업을 같은 트랜잭션에 저장해도, 성공 응답 직후 종료됐을 때 두 데이터가 함께 사라질 수 있었습니다. 메모리 DB 테스트와 정상 종료만으로는 확인하지 못한 문제였습니다.

`WRITE_DELAY=0`을 준 비교 실행에서 데이터가 남는 것을 확인한 뒤 파일 H2 URL에 반영했습니다. 내구성 수정 때는 Java 비즈니스 로직과 기존 15개 테스트를 그대로 두고, 설정과 회귀 검증 스크립트를 보완했습니다. 쓰기 비용은 늘 수 있지만 이 과제의 작은 처리량에 맞는 선택으로 봤으며, 성능 변화는 따로 측정하지 않았습니다.

추가한 스크립트의 시간대 표기 파싱 오류를 수정한 뒤, 체크인 응답 직후 강제 종료하고 같은 DB로 재시작하는 테스트를 **3회 다시 실행해 모두 통과**했습니다. 오류 재현부터 수정과 재검증까지 Codex가 진행했습니다.

## 테스트 및 직접 확인한 내용

### Codex가 실행한 테스트

Java 17에서 실행한 결과이며, 2026-10-31에 다시 확인했습니다. 실행 명령은 [README](../README.md#테스트와-확인한-내용)에 있습니다.

| 확인한 내용 | 결과 |
| --- | --- |
| `clean test bootJar` | 성공, JUnit 15개 통과. 실패·오류·건너뜀 0건 |
| SIGKILL 후 동일 파일 DB 재시작 | 3/3 통과 |
| Swagger UI · OpenAPI | 문서 생성·접속과 브라우저의 체크인·상태 조회 확인 |

JUnit에는 정상 발급, 일시 실패 후 성공, 총 4회 소진, 중복 체크인과 발급 후 타임아웃의 멱등 재시도가 있습니다. 동시 체크인 6건과 동일 작업의 동시 처리 요청 4건, 롤백 후 복구, 고유 제약과 HTTP 오류 응답도 확인합니다.

테스트는 메모리 H2와 Fake를 사용하고, 시계를 주입해 재시도 기한을 확인합니다. 롤백은 외부에서 연 트랜잭션에 예외를 던져 모사했으며, 실제 DB 커밋 장애를 일으킨 것은 아닙니다.

별도 [SIGKILL 스크립트](../scripts/verify_h2_durability.py)는 임시 DB와 JAR의 JDBC 설정을 사용합니다. 스케줄러를 끄고 체크인 응답 직후 종료한 뒤 같은 DB로 앱을 재시작했습니다. HTTP와 DB 조회로 `checked_in_at`, 발급 작업 1건, 최초 `requestId`, `PENDING`, `attempts=0`, `canEnter=false`가 남는지 확인했습니다. 체크인 시각은 최초 응답의 `nextAttemptAt`과 1마이크로초 이내로 일치했습니다.

결과는 `build/reports/tests/test/index.html`과 `build/h2-durability-result.json`에 남겼습니다. 생성된 JAR에 `WRITE_DELAY=0`이 들어간 것도 확인했습니다.

### 개발자가 Swagger UI에서 직접 확인한 내용

2026-10-31에 개발자가 로컬 서버와 `FakeDoorlockClient`를 사용해 직접 호출하고 응답을 확인했습니다.

| 확인한 상황 | 응답 |
| --- | --- |
| 정상 발급 — 예약 `1001` | POST: `202 Accepted`, `PENDING`, `attempts=0`. 이후 GET: `200 OK`, `ISSUED`, `canEnter=true`, `attempts=1` |
| 체크인 전 조회 — 예약 `1002` | 체크인 전에 GET을 요청해 `409 Conflict`와 “먼저 체크인해야 합니다.” 메시지 확인 |
| 일시 실패 후 복구 — 예약 `1002` | POST: `202 Accepted`, `PENDING`, `attempts=0`. 이후 GET: `200 OK`, `ISSUED`, `canEnter=true`, `attempts=2` |

정상 발급과 재시도 후 복구 모두 최초 POST와 최종 GET의 `requestId`가 같았습니다. 재시도 확인은 서버를 `DOORLOCK_FAKE_SCENARIO=TRANSIENT_THEN_SUCCESS`로 실행한 결과입니다. 중간 실패 상태를 Swagger에서 따로 캡처하지는 않았고, 설정한 Fake 시나리오와 최종 `attempts=2`가 일치하는 것을 확인했습니다.

## 설계하면서 고려한 부분

- 체크인 정보와 발급 작업을 같은 DB 트랜잭션에 저장해 둘 중 하나만 남지 않도록 했습니다.
- 처음 들어오는 중복 요청도 막기 위해 예약 행을 잠그고 예약별 작업 고유 제약을 뒀습니다. 워커도 작업 행을 잠근 뒤 상태와 처리 기한을 다시 확인합니다.
- 최초 호출 1회와 재시도 최대 3회, 총 4회까지 같은 `requestId`를 사용합니다. 외부 시스템이 같은 ID에 기존 발급 결과를 반환한다는 멱등성 보장에 의존합니다. DB 롤백 시 실제 호출 수는 커밋된 시도 수보다 많아질 수 있습니다.
- `ISSUED`일 때만 입실 가능으로 표시합니다. `FAILED`는 자동 재시도 종료이며, 실제 외부 미발급을 뜻하지 않습니다.
- 발급 호출 중에도 DB 잠금을 유지합니다. 구조는 단순하지만 외부 호출이 길어지면 DB 자원을 오래 점유하므로 실제 연동 시 타임아웃과 처리량을 살펴봐야 합니다.

## 구현 범위와 한계

- 별도 프런트엔드, 인증/인가, 결제, 실제 도어락 연동, 예약 생성·변경·취소와 권한 만료·회수는 만들지 않았습니다. 실제 외부 발급 상태 재조회, 운영자의 수동 복구와 알림도 없습니다. `canEnter`는 발급 확인 여부로, 실제 문이 열리는지나 권한이 만료됐는지를 확인한 값은 아닙니다.
- Fake의 멱등 기록은 메모리에만 있어 재시작하면 사라집니다. 외부 발급 직후 재시작까지 포함한 중복 발급 방지는 확인하지 않았습니다. 실제 외부 시스템의 네트워크 동작과 멱등 계약도 시험하지 않았습니다.
- 강제 종료 테스트는 외부 발급 전의 단일 Java 프로세스를 대상으로 했습니다. 전원 차단, 디스크 장애와 외부 발급 도중 강제 종료는 확인하지 않았습니다.
- 동시성 테스트는 한 프로세스의 실제 스레드로 실행했으며 모든 경합 순서를 통제하지는 않았습니다. 다중 인스턴스, 운영용 DB, 부하·장시간 장애, 보안 감사와 운영 배포는 확인하지 않았습니다. JUnit의 스케줄러 테스트는 자동 실행 대신 `poll()`을 직접 호출합니다.
